# Design decisions

The decisions that shaped the implementation, with the reasoning that produced them. Values read
from the design file are catalogued in [`design-spec.md`](design-spec.md); how the products
feature is laid out is described in
[`src/features/products/README.md`](../src/features/products/README.md).

## Stack

- **TanStack Form** — full type inference over nested values, per-step validation through
  `FormGroup` without splitting the form into three, and native standard-schema support for
  Zod 4. react-hook-form would also have worked; Formik is effectively unmaintained.
- **Zod 4** — one schema per step plus one for the whole form. Text becomes numbers in schema
  transforms, so conversion lives in one place and everything past the form boundary is fully
  typed.
- **nuqs** over a raw `useSearchParams` — a parser with a default, explicit `push`/`replace`
  history semantics, and a testing adapter that lets tests assert on the URL.
- **React context** over an external store — the catalogue is one value and one action
  (`addProduct`), and the context value is memoised. Zustand or Redux would add API surface
  with nothing to amortise it.
- **shadcn/ui on Base UI** — components generated by the CLI and kept in the registry's own
  formatting (see `.prettierignore`), so a future `shadcn add` diffs against the registry
  rather than against local style.

## Two halves and a kernel

An earlier layout sorted files by kind (`hooks/`, `utils/`, `types/`). Its cost showed in the
history: every change to the form's behaviour touched `add-product/` **and** a file in
`utils/`, and a types file had eight importers — all of them in `fields/`. A file with many
importers inside a single directory is not shared; it is misplaced.

### Where a file lives

Read by both halves → the kernel (`domain/`, `api/`, `stores/`, `hooks/`). Read by one → next
to its only reader, with its tests beside it. The direction is enforced by
`import/no-restricted-paths` in `eslint.config.mjs`, not just described. Imports into the
kernel and across features are absolute; imports within a half are relative, so a half reads
and moves as one unit.

## One form, three steps

A single `useForm` holds `{ basics, pricing, availability }`. Steps are views over that one
state, so going back never loses a value — nothing unmounts from the state. Each step gates
itself with its own schema through `form.FormGroup`; the whole-form schema runs once more at
save.

There is no form-level validator: it would report issues for every path on every blur, and
step 2 would open with its price fields already red.

"Dalej" is never disabled. Untouched fields count as valid, so a disabled button would start
active and switch off mid-typing; it also drops out of the tab order and cannot say why it
refuses. Clicking it reveals the step's errors and moves focus to the first invalid field.

Save has no error branch: the full schema has already passed and the catalogue lives in
memory. A real backend makes that branch the first addition (see the last section).

## Validation: checked vs shown

Two questions, answered in two places:

- **Checked** — a custom `ValidationLogicFn` runs the step schema on every change, blur and
  submit, so the store always holds a verdict on every field.
- **Shown** — a field reports its verdict only once its own blur flag is set. Nothing else in
  the step can force a field to speak.

The custom logic exists because each `revalidateLogic` mode leaves a gap: `change` skips blur
before the first submit, `blur` leaves a stale error under a field being corrected, and an
`onChange`+`onBlur` pair with the same schema doubles every message.

Clicking "Dalej" or "Zapisz" marks every field of the step blurred — the user has now seen the
whole step, and reusing the blur flag keeps "may show an error" a single concept.

Unchecking "Produkt limitowany" resets the stock field rather than hiding it: a stale value
would reach the saved product, and its old blur flag would paint the field red the moment it
returns.

## Focus

The keyed `FormGroup` remounts the whole step, which drops focus on `<body>`, so an effect
focuses the first field of the step the user moved to. After a failed submit, which fields are
invalid comes from the store (React has not painted `aria-invalid` yet) and which one to focus
comes from the DOM, because document order is what the user sees. An `aria-live` region
announces "Krok X z 3" — focus landing on a field does not say the step changed.

## Prices

- **State holds text, not numbers.** `Number('12.')` is `12` — the dot would vanish while the
  user is still typing. Conversion happens in the schema.
- **Arithmetic runs on whole grosze**, which is exact for every two-decimal amount; validation
  caps amounts at two decimals because a third reintroduces unrepresentable ties. A round-trip
  test covers 200 000 amounts at every VAT rate.
- **The authored side is remembered.** The user types one side, the other is derived, and a
  VAT change recalculates the derived side. Without this a typed gross of 100.03 at 23%
  drifts to 100.04 through its own net.
- **Mid-edit garbage leaves the sibling alone** — better a briefly stale value than a good one
  blanked mid-keystroke.
- **Ceilings.** Quantities stop at 999 999 999, far below 2^53, past which a typed number is
  silently stored as a different one. Both prices share one ceiling of 999 999 999.99, checked
  separately from the format so a too-long number reads "too large", not "badly written".

## Dialog

The dialog's content unmounts on close, so every open starts at step 1 with defaults — the
reset is structural, not a handler's duty. The brief specifies that closing resets the form,
so Escape and clicks outside reset without a confirmation step.

## Loading

The form loads lazily (`next/dynamic`, `ssr: false`) and is preloaded on hover, focus and
pointer-down of the trigger. Measured on the first page load: 1.30 MB → 729 KB (370 → 229 KB
compressed). The skeleton is its own file — importing it from the form module would pull in
the very bundle it stands in for. The header and stepper are static, so the skeleton renders
the real ones and nothing shifts when the chunk arrives.

## Pagination and data

The page number lives in `?page=`, so a refresh keeps the view. Paging pushes history; URL
corrections and the return to page 1 after a save use `replace` — pressing back must not look
like an undone save. Out-of-range and non-numeric values are clamped to a real page and the
URL is rewritten.

The seed is five products, as the brief specifies; the design shows seven. Where the two
disagree, the brief is the contract. VAT rates and currencies carry full option sets
(23/8/5/0, PLN/EUR/USD): the design shows only each select's default, and a single-option
select is a control in name only.

There is no empty state: the catalogue starts seeded and nothing deletes, so the state is
unreachable through the UI. Deletion would justify it.

## Design fidelity

Tokens — colours, radii, sizes — are transcribed from the `.fig` file into
[`design-spec.md`](design-spec.md). Where the design conflicts with itself, the consistent
variant wins: the step 2→3 connector colour, the description field's label. The focus ring
uses the primary colour — the design defines no focus states, and the default grey ring sits
below the 3:1 contrast requirement. Product features render as a `ToggleGroup` rather than
badges: the element presses and releases, so it reports `aria-pressed` and takes a single tab
stop with arrow keys between options.

## With a real backend

The in-memory store stands in for one. The first things it forces: an error branch on save
(the dialog stays open and says no), server-issued ids, loading and optimistic states on the
list, an empty state once deletion exists, and a query library in place of the context store.
